# Development Methodology

## 1. Software Development Lifecycle (SDLC)

- **Framework:** Iterative incremental. The prototype is built in short increments, each ending
  with a working, tested build on `main`. The increments so far follow the two phases of the
  SEG4105 term project:
  1. the triage pipeline, web application, ETL/ELT jobs and test suite;
  2. the project plan data, CPM / PERT / Monte Carlo simulation and analysis reports;
  3. report data collection, demo seed data, the benchmark, and this documentation and container
     packaging.
- **Planning & Tracking:** work items are logged as GitHub Issues in this repository. Each issue
  states the tasks and a "done when" condition, and is closed automatically by the pull request
  that completes it (`Closes #<number>` in the pull request description). The project plan itself
  (activities, dependencies, three-point estimates and costs) is kept as data in `sim/plan.py`, so
  the schedule and cost baselines can be recomputed with `python sim/monte_carlo.py`.

## 2. Version Control & Branching Strategy

- **Workflow:** GitHub Flow.
- **`main`:** always contains runnable, tested code. Nothing is committed to `main` directly once
  the repository is shared; changes arrive through pull requests.
- **`feature/*` | `fix/*` | `docs/*`:** short-lived branches created from an up-to-date `main` for
  one isolated change. A branch is deleted on GitHub and locally after its pull request is merged.
- **Commit Convention:** `Type: short imperative summary`, where the type is one of `Feat`, `Fix`,
  `Docs`, `Test`, `Refactor` or `Chore` (for example `Docs: add components, architecture, and
  methodology specs`). One logical change per commit.
- **Ignored files:** generated data (`data/*.db`, `data/*.pkl`, `data/*.csv`), caches, virtual
  environments, logs and `.env` files are listed in `.gitignore` and are never committed.

## 3. Code Review & Definition of Done (DoD)

A change is done when all of the following hold:

1. Code runs locally without errors or regressions (`uvicorn app.main:app` starts and `/health`
   returns `ok`).
2. Unit and integration tests pass (`pytest`), and `ruff check .` reports no findings.
3. Relevant documentation (`README.md` and `/docs`) is updated in the same pull request.
4. Changes are submitted via pull request and reviewed by the other group member before merging
   into `main`. Review comments are answered or fixed on the same branch.
5. The linked issue is referenced in the pull request so it closes on merge.

## 4. Testing & Quality Assurance Strategy

- **Unit Testing:** pytest with pytest-cov, branch coverage enabled over `app` and `etl`
  (configured in `pyproject.toml`). Target: at least 90% branch coverage. The last recorded run
  (`docs/reports/pytest_coverage.txt`) shows 79 tests passing and 92% coverage. Unit tests cover the
  pipeline, classifier, redaction, GIS and ETL modules; `tests/conftest.py` trains a small model so
  tests do not depend on generated data.
- **Integration / System Testing:** `tests/test_api.py` drives the HTTP routes end to end through
  FastAPI's test client against a temporary database. `scripts/benchmark.py` pushes 1,000 generated
  requests through the whole pipeline to measure throughput and latency
  (`docs/reports/benchmark.txt`). The container image is checked by building it, running it and
  calling `/health`.
- **Static Analysis:** `ruff check .` for style, likely bugs and cyclomatic complexity (limit 10);
  `bandit -r app etl sim -c pyproject.toml` for security findings. Results are kept in
  `docs/reports/`.
- **Test data:** all data is synthetic and generated by `etl/generate_history.py`; no real
  resident or city data is used.
